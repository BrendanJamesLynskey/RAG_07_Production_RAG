01

Demo to Production — The Real Work

A RAG prototype can be built in an afternoon. A production RAG system is a different class of problem: it must be correct, fast, secure, cost-predictable, and observable — at scale, continuously, over a corpus that drifts.

What the demo ignores

  • Eval: is the system actually correct?
  • Drift: the corpus ages; the embedding model will be superseded
  • Tenancy: user A must not see user B's documents
  • Cost: at 10 k queries/day, what is the monthly inference + index bill?
  • Failure handling: what happens when retrieval returns nothing?
  • Latency at P99: one slow reranker call makes the SLA miss

The production maturity ladder

Level 0: Works in a notebook. Level 1: Deployed with a golden test set showing >80% answer faithfulness. Level 2: Continuous eval, alerting on metric drops. Level 3: Embedding drift monitoring, A/B testing infra, multi-tenant isolation. Level 4: Full cost attribution per tenant, SLA-backed latency, abstention policies.

The most underrated production investment

The single highest-leverage investment in a production RAG system is a labelled evaluation set of 200–500 question–answer pairs drawn from real user queries. Without it, you cannot measure whether a change improved or regressed the system. With it, every infrastructure decision (new embedding model, chunk size change, reranker swap) becomes an empirical measurement rather than a guess.

RAGAS evaluation (v0.2) — minimal setup
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_recall
from datasets import Dataset

eval_data = {
    "question":         ["What is HNSW?", ...],
    "contexts":         [["HNSW is a graph-based ANN..."], ...],
    "answer":           ["HNSW stands for Hierarchical...", ...],
    "ground_truth":     ["Hierarchical Navigable Small World...", ...],
}

result = evaluate(
    dataset=Dataset.from_dict(eval_data),
    metrics=[faithfulness, answer_relevancy, context_recall],
)

Drift & Freshness — Embedding Migrations, A/B Tests

RAG systems degrade over time from two distinct sources: corpus drift (the world changes; indexed documents become stale) and model drift (a better embedding model is available but the index still uses the old one).

Corpus freshness

Monitor doc_modified_at vs ingested_at lag. Alert when >5% of the corpus is stale by more than N days. Use change-data-capture (CDC) from the source system (Postgres WAL, S3 event notifications, Kafka) to trigger incremental re-ingestion. Freshness is not free: every re-ingested document costs one embedding call.

Embedding model migration

Never mix embeddings from two different models in the same index. Old and new model vectors live in different metric spaces; cosine similarity across them is meaningless. Migration plan: build a shadow index with the new model; run A/B traffic; cut over atomically via collection alias swap. Shadow index build time at 100 k docs / 768 dims / BGE-base: ~20 min on A10G.

A/B testing RAG changes safely

A/B test any significant change (new embedding model, new chunk size, new reranker) before full rollout. Serve variant A to 90% of traffic, variant B to 10%. Measure: RAGAS Faithfulness, Answer Relevancy, Recall@10, user thumbs up/down rate, query latency P50/P99. Run for 72 hours minimum to account for daily query distribution variation. Use a hash of the user ID or session ID for stable assignment — never random per request or you'll show the same user both variants for the same query.

Latency Budgets — Caching, Prefetching, Query Rewriting

RAG latency is dominated by two serial operations that cannot easily be parallelised: embedding the query and LLM generation. Everything else can be optimised to negligible cost.

Multi-Tenancy — Namespaces, ACLs, Secure Retrieval

Multi-tenant RAG is a security-critical design. A tenant isolation failure allows one customer to retrieve another customer's documents — a data breach.

Namespace isolation

One vector DB collection per tenant. Complete data isolation; no cross-contamination possible. Simplest to implement and audit. Cost: collection-level overhead multiplied by N tenants. Suitable for <1000 tenants. Pinecone namespaces, Qdrant collections, Weaviate classes, pgvector schemas all support this model.

Shared collection + payload filter

All tenants in one collection. Every vector carries a tenant_id payload field. Every query includes a mandatory filter. More efficient but requires that the filter is always applied — one missing filter = cross-tenant leak. Enforce at the retrieval service layer, not the application layer. Qdrant's payload indexes make this efficient.

ACL-based fine-grained access

Each document has an ACL list of user/group IDs. At query time, filter to documents where the user's ID or group appears in the ACL. Enables row-level security across tenants and roles. Implementation: store ACL as a JSON array payload field; Qdrant supports array-contains filters. For >1 M documents per tenant with complex ACLs, consider a dedicated access control service.

The injection attack surface

Multi-tenant RAG must guard against prompt injection via retrieved documents: a malicious document in tenant A's corpus could contain instructions that leak tenant B's context if A and B share an LLM session. Mitigate with: (1) strict namespace isolation at the retrieval layer, (2) sanitise retrieved text before inserting into the LLM prompt, (3) instruct the model with a system prompt that forbids acting on instructions found in retrieved context. This is an active research area — no complete solution exists yet.

Citation & Grounding — Quoting Sources, Traceability

Enterprise RAG users require answers to be grounded in sources — both for trust and for auditability in regulated industries (legal, medical, financial). Citation is not a cosmetic feature; it is the mechanism by which users verify correctness.

Citation prompt pattern (Claude/OpenAI)
# System prompt
system = """
You are a precise research assistant. Answer only from the provided context.
For each claim, include an inline citation [1], [2] referencing the source chunk.
If the context does not contain the answer, say "I don't have enough information."
Never invent sources or cite documents not in the context.
"""

# Context block (each retrieved chunk labelled)
context = "\n\n".join([
    f"[{i+1}] (Source: {c['source']}, p.{c['page']})\n{c['content']}"
    for i, c in enumerate(retrieved_chunks)
])

# User message includes context + question
user = f"Context:\n{context}\n\nQuestion: {query}"
Faithfulness vs hallucination detection

RAGAS Faithfulness checks whether each sentence in the generated answer is entailed by at least one retrieved chunk. Score = (faithfully-grounded sentences) / (total sentences). A score below 0.85 indicates the model is extrapolating beyond its retrieved context. Use Trulens' real-time groundedness check as a guardrail: if faithfulness drops below threshold, append a disclaimer to the response or escalate to a human reviewer. Never surface answers with faithfulness < 0.7 without explicit user warning.

Cost — Embedding Refresh, Vector DB Pricing, Reranker Inference

Cost modelling is essential before committing to infrastructure choices. The largest RAG cost drivers are often not the LLM generation but the embedding and vector DB layers.

The dominant cost is almost always LLM generation

For a 10 k query/day system at 5 retrieved chunks × 500 tokens each, the input context alone is 25 M tokens/day. At GPT-4o-mini prices ($0.15/Mtok), that is $3.75/day. At Claude Sonnet ($3/Mtok): $75/day. The reranker and embedding costs are a rounding error by comparison. Reduce LLM cost first: use contextual compression to extract only the relevant sentences from each chunk before inserting into context (LangChain LLMChainExtractor). A 50% context reduction at the same answer quality halves your LLM bill.

Failure Modes — Empty Results, Low Confidence, Abstention

A production RAG system must handle retrieval failures gracefully. Silently returning hallucinated answers is worse than explicit abstention.

Abstention as a first-class feature

Design explicit abstention into the system. If context relevance is below 0.5 (RAGAS), return: "I couldn't find reliable information in the knowledge base for this question. Please consult [source] or contact [team]." This is not a failure — it is correct behaviour that prevents low-quality hallucinated answers from eroding user trust. Track abstention rate as a metric; a sudden spike indicates corpus freshness or retrieval pipeline issues.

09

What to Take Away

  • Build a labelled evaluation set first. 200–500 question–answer pairs from real users. Everything else depends on it.
  • RAGAS is the standard eval framework. Faithfulness, Answer Relevancy, and Context Recall are the three metrics every production RAG system must track continuously.
  • Never mix embedding models in a single index. Use shadow index + alias swap for zero-downtime embedding migrations.
  • Multi-tenancy requires either namespace isolation or mandatory payload filters. There is no safe middle ground. Enforce at the retrieval service layer.
  • Citation and groundedness are enterprise requirements, not optional polish. RAGAS Faithfulness < 0.7 requires an explicit user warning or abstention.
  • LLM generation dominates cost. Contextual compression (extracting only relevant sentences) is the highest-leverage cost optimisation. The embedding and reranker costs are secondary.
  • Build abstention into the system. Monitor context relevance; return explicit "I don't know" rather than confident hallucination when retrieval quality is low.
  • A/B test every significant change (chunk size, embedding model, reranker) against your labelled eval set before full rollout.
